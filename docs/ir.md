# Mentat Bench — wire formats (contract between Rust engine and Python harness)

Normative semantics: `SPEC.md` (the specification of 2026-10-27). This file fixes the JSON shapes and engine/CLI behaviour.
All files are UTF-8 JSON / JSON-lines (a leading BOM is tolerated on every input the engine reads). Python never does logical inference; the Rust `mb-engine` CLI does.

## IDs
Outcome ID = string `"<venue>:<market_id>:<outcome_index>"` (e.g. `polymarket:123:1`, `toy:m17:2`). Only outcome IDs are free Boolean variables. IDs must be unique within `bindings.jsonl`.

## Expr (JSON object, `op` discriminates)
`{"op":"true"}` `{"op":"false"}` `{"op":"var","id":ID}` `{"op":"ref","name":ALIAS}`
`{"op":"not","a":E}` `{"op":"and","args":[E..]}` `{"op":"or","args":[E..]}`
`{"op":"implies","a":E,"b":E}` `{"op":"iff","a":E,"b":E}`
`{"op":"atmost"|"atleast"|"exactly","k":int,"args":[E..]}`
`{"op":"wsum","cmp":"le"|"ge"|"eq","k":int,"terms":[{"w":int,"e":E}..]}`  (sum of w*[e] cmp k)

Validation rules (error code in parentheses; `validate` exits 1 and prints a JSON error list):
- Unknown keys are rejected on every Expr object except `true`/`false` (serde limitation for unit variants), and on bindings, constraints, terms, provenance records, queries and answers.
- `ref` targets an alias. Alias definitions must be acyclic through `ref` (`alias_cycle`); implication cycles via `implies` constraints are fine. Alias names must be unique (`duplicate_alias`).
- A bound outcome is a literal equivalence with its class alias. Build the alias graph with edges alias→`ref` target and alias→(variable)→class it is bound to. A **non-literal** alias definition (anything other than `var(id)` / `not(var(id))`) lying in a multi-node strongly connected component, or with a self-loop, is rejected (`alias_binding_cycle`): such a binding would inject a hidden implication. Literal definitions are exempt and may sit on cycles (that is how the harness and generators represent equivalence classes, including mutually bound literal aliases).
- `interps`, when present, must be non-empty (`empty_interps`).
- Nesting depth is capped at 100000 (`cap_depth`; the profile key `max_expr_depth` may lower it); query expressions are checked per line against `min(max_expr_depth, 100000)` and deeper lines become `bad_query`. Each JSON document may nest at most 250000 levels (beyond that: `parse_error` for bindings, theory and provenance, `profile_invalid` for `profile.json`, `bad_query` for a query line; measured stack use is ~1 KiB per level on the 512 MiB worker). The JSON parser has no 128-level limit.
- `max_expr_nodes` is a **total** budget over all alias definitions and constraints (each node counted once; a `ref` leaf counts 1; `cap_expr_nodes`).
- `max_weight_bits` bounds every weight, every `wsum` constant `k`, and every cardinality `k` (`cap_weight_bits`). The sum of |w| of one `wsum` must be at most 2^62 (`cap_weight_sum`; covers i64::MIN).

## Submission directory (output of `build`, input of `seal`/`evaluate`)
- `bindings.jsonl`: one per eligible outcome: `{"id":ID,"status":"bound"|"unresolved","class":ALIAS|null,"negated":bool,"missing":[CODE..],"evidence":[REF..]}`.
  `bound` means `var(id) <-> class` (or its negation if `negated`); `class` names an alias. `unresolved` has `class:null` and `missing` qualifier codes (e.g. `no_date`, `no_source`); the atom keeps Boolean identity. Evidence may include `src:<market>:event_title`.
- `theory.json`: `{"interpretations":["base"],"aliases":{NAME:Expr},"constraints":[{"id":CID,"expr":Expr,"interps":null|[IID..],"provenance":[REF..]}]}`.
  A constraint holds in every interpretation in `interps` (null = all). Constraint ids: pairwise relations `p{n:07d}`, group constraints `g{n:07d}`, ordered-chain links `g{n:07d}.{i}`. With scoped group decisions the interpretations are the cross product over the scope axes, named `axis=value|axis=value` (axes in name order, capped by `max_interpretations`); without scopes they are `["base"]`. Group kinds compile to: `exactly_one` -> `exactly` k=1; `at_most_one`/`at_most_k` -> `atmost`; `at_least_k` -> `atleast`; `ordered_chain` -> one `implies` per link (no wire change). Definitive relations must hold in all admissible interpretations; alternatives let interpretations disagree. Constraint provenance is the union of its outcomes' question REFs, the defining question REFs of the aliases it uses, and any supplied REFs (axioms, event titles); constants-only constraints may have `[]`.
- `provenance.jsonl`: `{"ref":REF,"kind":"source"|"axiom","record":"<market_id|event_id|AXIOM_ID>","field":"..."}`. REF shapes: `src:<market>:question`, `src:<market>:outcome_label:<idx>`, `src:<market>:event_title`, `src:event:<event_id>:event_title`, `ax:<AXIOM_ID>` (kind `axiom`, field `rule`). Every nontrivial binding/constraint cites >=1 REF that exists here.
- `usage.json`: `{"calls":[{"model":str,"kind":"llm|embedding|local","tokens_in":int,"tokens_out":int,"seconds":float,"cost_usd":float,"retry":bool?,"items":int?,"gpu_seconds":float?,"op":"decide_binding|decide_relation|decide_group"?}],"wall_seconds":float,"peak_rss_mb":float}`. `retry` is optional (default false); `items` is optional (integer >= 1, the number of decisions the call carried, default 1: a batched call is ONE aggregate usage record); `torn` is optional (`true` marks the placeholder a resume wrote for a usage row a kill cut mid-write: items = the build's batch_size, cost 0; docs/local_protocol.md, Resume), and a top-level `torn_usage_rows` (the count of those rows) is present only when nonzero; `gpu_seconds` is optional (finite, >= 0); `child_cpu_seconds` and `child_peak_rss_mb` are optional (finite, >= 0; local children only: the CPU seconds the child's process tree used since the previous usage record, and its peak resident MB so far; sampled at most once per `SAMPLE_EVERY_S` = 0.5 s, so responses inside the interval carry no child fields and the totals cover the sampled intervals; `usage_totals` sums the first and takes the maximum of the second); `seconds`/`cost_usd`/`wall_seconds`/`peak_rss_mb` are finite and non-negative, token counts are non-negative integers. A call that overshoots the spend ceiling or the build deadline is charged but its decision is not accepted; it is the LAST usage entry of a build that stopped at it; a resume that clears the stop continues after it, so the overshooting call is then followed by the resumed run's calls, and the resumed build's pinned profile holds the extended limits. `evaluate` checks `sum(cost_usd) <= spend_ceiling_usd` and `sum(seconds) <= build_deadline_s` against the pinned profile over all calls except that last one (the last call is still schema-checked); an overshoot anywhere earlier is refused.
- `PARTIAL.json` (optional): `{"partial": true, "reasons": [...]}`, written beside a complete build that stopped at a cap or budget (`budget_stopped`, `pairs_capped`, `calls_capped`, `group_budget_stopped`, `deferred_unresolved`); it is hashed into the seal, `seal` still accepts it, and `evaluate` warns on stderr and adds `"partial": [reasons]` to its stdout JSON. `report.py` shows a STATUS column (complete / incomplete / the first partial reason).
- `build_id.json`: random 32-hex build identity, written at build time (or created by `seal` if absent) and sealed with the submission.
- `build_policy.json` (optional, written by `build`, sealed, not read by the engine): `{adapter, model (the child's hello model block), top_k (blocking partners per market; the CLI default is 64, README.md), complement_dedup, batch_size (effective), max_pairs, max_calls, max_group_drops, max_group_drop_frac, max_relation_drop_frac (drop caps are NOT compared on `build --resume`), groups_disabled_reason (null when the group phase ran; otherwise flag | full_replay | adapter_no_groups | hello_timeout | hello_error | hello_failed | no_decide_group, see docs/local_protocol.md), groups, group_sources, group_max_members (effective), group_budget_frac, max_group_calls, max_df, max_relation_drops, admit (base consistency by admission; false: post-hoc repair), admit_max_literals (admission runs when 2 x outcomes is at most this), relation_floor (null: no floor), repair_budget_s (null: the repair runs to the deadline)} on the pairwise path these are the requested values, null on the full-replay path and with probe off (admit_mode says whether admission ran)}` harness knobs and the adapter name (the profile is strict, so knobs live here; `evaluate` warns on stderr for oracle / gold_view submissions).
- `profile.json`: the resource profile the build ran under (see below); it is sealed with the submission and must equal the profile pinned at evaluation.
- `seal.json` (written by `seal`): exactly `{"digest":sha256,"files":{relpath:sha256}}`. Paths are POSIX relative paths and may include subdirectories (hashed recursively); symlinks are refused. Reparse points (symlinks, junctions) are refused. A directory is sealed once: `{build_id, digest, sealed_at_utc, submission}` is appended to `<submission parent>/seal_ledger.jsonl` (under an exclusive OS lock on `seal_ledger.oslock`), and a build_id or path with a ledger entry cannot be sealed under another digest even if `seal.json` is deleted or the directory is renamed (a deleted `seal.json` of an unchanged directory is written back with the ledgered digest). (Known limits: deleting `build_id.json` and renaming defeats the check, and the ledger is per parent directory, so moving a sealed submission to a different parent and re-sealing is not caught; keep external copies of the ledger. A build that stopped with `adapter_fatal` (or `groups_fatal`) writes `INCOMPLETE.json` into its output; `seal` refuses such a directory (exit 4, naming the reason) unless `--allow-incomplete` is given, in which case the marker is hashed into the seal, and `evaluate` prints a stderr warning and adds `"incomplete": true` to its stdout JSON.) The ledger entry is appended BEFORE `seal.json` is written (both fsynced; on POSIX the directory is fsynced too), so every `seal.json` has its ledger entry. Outcomes: a ledger append that fails before the entry persists leaves no entry and no seal, and the directory stays sealable. A `seal.json` write that fails after the append keeps the entry (it is not removed), and the next seal writes `seal.json` with the same digest. A hard kill between the two writes leaves an entry without `seal.json`: the default `evaluate` (which does not consult the ledger unless `--ledger` is given) refuses the directory as not sealed, and so does `evaluate --ledger`; sealing it again writes `seal.json` with the ledgered digest, but only when the directory still hashes to that digest, and a directory changed since is refused ("changed since it was ledgered"). A directory is never sealed under a second digest. A `seal.json` whose build_id and path have no ledger entry is refused as sealed, never completed. A partial or malformed ledger line makes every seal on that ledger refuse (it fails closed).

## Sealing (`seal`, `seal_ledger.jsonl`)

The code is `python/mentat_bench/seal.py`; the rules below are what its tests check.

**Order of a seal.** (1) Under the ledger lock, `build_id.json` is read or created; then every listed file is marked read-only and the listing (name, size, mtime, ctime, mode) is taken. (2) Outside the lock, on the read-only files, every file below the submission is hashed; the digest is the SHA-256 of the sorted `name hash` lines. (3) Under the lock, `seal.json`, the listing, `build_id.json` and the ledger are checked again. (4) The ledger entry `{build_id, digest, submission, sealed_at_utc}` is appended and fsynced before `seal.json` exists, so every `seal.json` has its entry. (5) `seal.json` is published as a temp file beside the submission (`<parent>/.seal.json.<hex>.tmp`, outside the sealed listing), hard-linked to `seal.json` (a link never overwrites), and the temp file is removed. The directory is fsynced on POSIX.

**Kill window and recovery.** A kill between (4) and (5) leaves an entry without `seal.json`. `evaluate` refuses that directory (not sealed). The next `seal` publishes `seal.json` with the SAME digest, but only when the directory still hashes to the ledgered digest under the lock; a directory changed since is refused ("changed since it was ledgered"). A `seal.json` that is present but malformed or zero-length (torn) is replaced under the same condition, and refused otherwise with a message naming the file to delete. A `seal.json` with no ledger entry for its build_id and path is refused as sealed, never completed. Deleting a `seal.json` of an unchanged directory and sealing again writes it back with the ledgered digest. A directory sealed under one digest is never sealed under another.

**Failures.** An append that fails before it persists leaves no entry and no seal, and the ledger is truncated back to its size before the append (a partial line never stays). A `seal.json` publish that fails after the append keeps the entry, and the next seal publishes `seal.json` with the same digest. A seal that fails before it publishes undoes its own work while nothing seals the directory: under the lock it restores the write access it removed and removes the `build_id.json` it created (also when a torn `seal.json` without an entry was the reason). A directory with a ledger entry, or a valid `seal.json`, keeps its marks. The marks also stay in these cases: a lock timeout at the first lock (nothing was marked yet); a lock timeout at the second lock (the `build_id.json` and the marks stay, because the undo needs the lock too); a hard kill (the next seal keeps the marks and seals on); and an undo that cannot take the lock (a warning names what was left). In those cases the read-only flag must be cleared to edit the directory. A failed mark on a `seal.json` that was just published is a warning, not a failed seal. If a temp or `seal.json` file cannot be removed, the error names it. `seal` exits 4 for any seal error, including a lock that is not taken within the wait and a ledger that cannot be used.

**The lock.** The ledger lock is an OS lock on `seal_ledger.oslock` (the ledger's name with `.oslock`): `msvcrt.locking` on Windows (one byte, non-blocking tries until the wait ends) and `fcntl.flock` on POSIX. The lock file is created on first use and never removed. The lock belongs to the open handle, so the OS releases it when the handle closes or the process dies: a killed seal leaves no lock behind, and there is no owner record, stale judgement or age limit. A seal waits up to 20 s (`LOCK_WAIT_S`) for the lock, then exits 4 naming it. Hashing is never done under the lock. Builds before this lock used `seal_ledger.lock` (the ledger's name with `.lock`), with an owner record, and removed it as stale after 600 s. The two builds never touch each other's lock file, but neither waits for the other's lock: seals by both on one ledger are not excluded. Concurrent seals may both pass their checks and append, and a later seal of that directory is then refused. Do not run the two builds at once.

**The ledger.** `MB_SEAL_LEDGER` names a central ledger; a relative name is resolved to an absolute path when the seal runs, so it must name the same file for every seal. Without it, the ledger is `seal_ledger.jsonl` beside the submission. A ledger whose name is its own lock file's name (`.oslock`, or `.lock`, in any case on Windows) is refused. Under the lock, before each entry is appended, a final line that has no newline and is not a complete entry is cut: it is what an append left when it was killed before its fsync, and its `seal.json` cannot exist, since `seal.json` is published after the append. A complete final line without its newline is kept, and the next entry starts on its own line. Until a seal cuts an unfinished last line, `evaluate --ledger` fails closed on it. The ledger protects the entry of each build_id and path: a directory with an entry is not sealed under a second digest, and a `seal.json` without an entry is refused. It must be one intact local file: a partial or malformed line makes every seal on that ledger refuse (it fails closed, for every directory on it). It does not protect against deleting or rewriting the ledger together with `seal.json` and the files (copy the ledger out for external audit); against a sealed directory moved under another parent with the default per-parent ledger (use `MB_SEAL_LEDGER` for one central file, which also matches the build_id); or against deleting `build_id.json`. The default `evaluate` does not read the ledger; `evaluate --ledger` (`verify_ledger`) checks the sealed digest against the entry of the directory's build_id.

**Limits.** The listing compares names, sizes, mtimes, ctimes and modes on every platform, not contents. The marks are set before hashing, so an ordinary write fails while a seal runs; an edit must clear the mark first, which changes the mode the listing compares. On Windows `st_ctime` is the creation time: it catches a file replaced whole, not a write, so an edit that clears the mark, keeps the size, restores the mtime and sets the mark again before the lock is not seen there. The lock works on a local volume only: `flock` and byte-range locks may not be enforced on network filesystems (NFS, SMB), and seal cannot detect that, so seal on a local volume. seal refuses a submission on another volume than its parent, because `seal.json` is hard-linked from the parent, and it probes for hard links before it writes anything. The listing is not checked again between the ledger append and the publish of `seal.json`: an external writer that gets past the mark in that window leaves a `seal.json` whose digest does not match the files, which `evaluate` reports as modified. A path-only ledger entry (the path was sealed under another build_id) is refused, and its directory keeps its marks until someone clears them. A sealed directory cannot be removed with a plain `shutil.rmtree` on Windows, because its files are read-only: clear the read-only bit first, as `cli._remove_tree` does; seal has no removal helper. A torn `seal.json` can come only from a file written by an older version or from disk damage, and it is never accepted unless the ledger matches. Test coverage: the Windows lock is tested with real processes (contention with three seals queued on the lock, a killed holder, concurrent seals of one directory); the POSIX branches (`fcntl.flock`, the directory fsync, the mount check) are tested through mocks only and have not been run on POSIX.

## Queries (`queries.jsonl`, one per line; engine reads, never sees gold)
Common: `{"qid":str,"family":F,...}`; optional `"universe":[ID..]` (default: every ID in bindings). `qid`s must be unique: a duplicate is an invalid workload (`eval`/`check` exit 2 with no output). A line that does not parse but has a recoverable qid yields `{"qid":...,"error":"bad_query"}` (and `query_invalid` in `check`) and is exempt from the duplicate-qid check; a line with no recoverable qid gets no answer (a note goes to stderr). Evaluation continues.
- `closure`: `"hyp":[Expr..]` (joint hypothesis H).
- `selection`: `"relation":"equiv"|"implies"|"implied_by"|"excludes"`, `"target":Expr`. p qualifies if theory ⊨ (p⇔target) / (p⇒target) / (target⇒p) / ¬(p∧target) in all interpretations, p's meaning established (bound).
- `feasibility`: `"assume":[Expr..]`.
- `partition`: `"members":[Expr..]`, `"claim":"exclusive"|"exhaustive"|"partition"`, `"target":Expr|null` (null = whole world). exclusive: pairwise ¬(mi∧mj); exhaustive: target ⇒ ∨mi; partition: both plus each mi ⇒ target.

Optional `"certificate": bool` (default false; only partition queries use it; `null` is `bad_query`) asks `eval` to attach a certificate to `true` answers. Optional `"evidence":[REF..]` (any family) scopes a query: only constraints whose provenance refs are ALL in the evidence (empty provenance always passes) and bindings whose evidence refs are all in the evidence are used; the default universe is the in-scope bindings in file order. An empty evidence list or an unknown ref answers `{"qid","error":"out_of_scope"}`; an expression variable whose binding is out of scope is `out_of_scope`; an explicit universe entry whose binding is out of scope is kept as unresolved (class null, `missing` gains `out_of_scope`). **Reach rule:** a constraint is kept only if all its provenance refs are in the evidence AND every outcome it reaches (directly, or through the alias definitions it uses, transitively) is in scope (binding evidence all in the evidence). A constraint that under-cites (provenance not covering the outcomes it reaches) is therefore silently dropped in scopes: citing correctly is the builder's responsibility. A bound in-scope outcome whose class reaches out-of-scope outcomes becomes unresolved (class null, `out_of_scope` appended to `missing`). Dropping constraints is NOT monotone for answers: feasibility can flip UNSAT to SAT and a `true` partition can become `false`; only base consistency is preserved. `"evidence": null` is rejected (`bad_query` in eval, `query_invalid` in check). For error or missing answers, `check` returns `answer_error` / `missing_answer` before scoping, so scope validity is not revealed (a well-formed non-error answer still distinguishes `query_invalid`). Scoped worlds are owned and cached up to 8 distinct canonical scopes (oldest evicted); the whole queries file is read at once, so peak memory grows with the evidence bytes in the file. Evidence-free queries behave exactly as before. A consistent full base implies a consistent scoped base (dropping constraints only weakens the theory), so no per-scope consistency check is needed. `check` verifies a scoped query against gold restricted to the same evidence; `out_of_scope` maps to `query_invalid`. Scoped queries run on a fresh component-partitioned world over the restricted submission (one engine under `MB_MONOLITH`).

Queries must not contain `ref` nodes (source IDs and operators only); `eval` answers such a query with `{"qid","error":"ref_in_query"}` and `check` gives it `cert_valid:false`, reason `query_invalid`. A `wsum` overflow or unknown ID in a query yields `{"qid","error":"weight_overflow"|...}` in `eval` and `query_invalid` in `check`.

## Answers (`answers.jsonl`)
Query-level failures yield `{"qid","error":str}` and evaluation continues (such an answer scores 0). A duplicated qid in an answers file is `answer_error` for that qid in `check` and scores 0 in `score`; a malformed answer line only affects its own qid.
- closure: `{"qid","labels":{"ENTAILED":[ID..],"REFUTED":[..],"CONTINGENT":[..],"UNRESOLVED":[..]}}` — every universe ID exactly once. Per interpretation: ENTAILED/REFUTED if K∧H forces var/¬var (priority even if unresolved); else CONTINGENT if bound, UNRESOLVED if status unresolved. Across interpretations: ENTAILED/REFUTED only if all agree; CONTINGENT only if all say CONTINGENT; otherwise UNRESOLVED. If no interpretation is consistent with H: `{"qid","labels":null,"error":"hyp_inconsistent"}`.
- selection: `{"qid","ids":[ID..]}`.
- feasibility: `{"qid","decision":"SAT"|"UNSAT"|"UNRESOLVED","witness":{ID:bool}|null,"core":[assume_index..]|null,"missing":[CODE..]}`.
  SAT in every interpretation → `SAT` with a **maximal partial witness** (for a witness W over the query support S: for every x in S not in W and each polarity v, W∪{x=v} fails to extend to a model in at least one interpretation; in a single interpretation a maximal witness is therefore total over S): an assignment over IDs of the query support (keys outside the support are `witness_invalid`) that extends to a model of every interpretation (plus the assumptions) and cannot be extended by any further support ID in either polarity (it may be `{}` only if no ID can be fixed). UNSAT in every interpretation → `UNSAT` (core = indices into `assume`, not necessarily minimal). Interpretations that disagree → `UNRESOLVED` (+ `missing` codes).
- partition: `{"qid","decision":"true"|"false"|"UNRESOLVED","counterexample":{ID:bool}|null,"missing":[CODE..],"evidence":[REF..]?}`. A `true` answer may carry a CERTIFICATE `evidence` (source + axiom refs): `check` first drops silently every ref that is not gold provenance or, for a scoped query, outside the query's evidence (so verdicts do not reveal ref membership), then accepts the answer only if the claim is entailed in every interpretation of gold restricted to exactly the remaining refs (reasons: `certificate_too_large` when the distinct refs AS WRITTEN exceed the cap, checked first; `claim_not_entailed` when the scope is too small, including a claim outcome outside the certificate scope; `certificate_missing` when the query asked for a certificate with `"certificate": true`, the answer is `true` and carries no evidence). An answer to a query WITHOUT the flag and without `evidence` keeps the old behaviour (certified when the full-gold claim holds). Evidence on non-`true` answers or other families is ignored. `eval` attaches a certificate to `true` answers when the query asks with `"certificate": true`: Zeller ddmin over the sorted refs, seeded with the refs reachable from the claim's outcomes (fallback: all refs of the claim's components); entailment is monotone in the ref set, so the result is 1-minimal unless the budget of 2048 entailment tests is spent; if the result exceeds the cap `eval` answers `{"qid","error":"certificate_too_large"}`; if the budget runs out above the cap, or the claim's components do not entail the claim, `certificate_error`; certification shares the query's single deadline (`timeout`). `true` iff the claim is entailed in every interpretation; `false` iff it fails in every interpretation, with a maximal partial counterexample (same maximality rule); otherwise `UNRESOLVED`.
- `missing`: unique non-empty strings, at most 8; absent or null means `[]`; a violation is `missing_invalid` in `check`. For an `UNRESOLVED` decision it must overlap the gold's codes for the query support (or both sides are empty). `missing` is derived from unresolved bindings in the support; an UNRESOLVED caused only by interpretation disagreement over bound atoms has `missing:[]`.

## `mb-engine` CLI (Rust, `crates/mb-engine`, binary name `mb-engine`)
- `mb-engine validate <submission_dir> [--profile profile.json]` → exit 0 / 1 + JSON error list on stdout.
- `mb-engine eval <submission_dir> <queries.jsonl> <answers.jsonl>`; applies `<submission_dir>/profile.json` caps through the same validator.
- `eval` stdout (exit 0 only): exactly one newline-terminated line, printed after the answers file is flushed, with keys in this order: `{"mb_engine_digests":{"theory.json":H,"bindings.jsonl":H,"provenance.jsonl":H,"profile.json":H,"queries":H,"answers":H},"version":V}`. The `"profile.json"` key appears only when `<submission_dir>/profile.json` is used. Each H is the lowercase SHA-256 of raw bytes: the submission files as read (BOM included), `profile.json` as read, `queries` as the bytes parsed (CRLF and a missing final newline included), `answers` as the bytes written. V is the mb-engine crate version. An eval error exit (1 or 2) prints nothing on stdout; exit 1 errors are a JSON error list on stderr, exit 2 errors are one plain `mb-engine: ...` line on stderr. `validate` stdout is unchanged (its JSON error list, `[]` when valid); `check` stdout is unchanged (empty).
- `mb-engine check <gold_dir> <queries.jsonl> <answers.jsonl> <verdicts.jsonl> [--max-certificate-refs N]` (N >= 1 overrides the gold profile's `max_certificate_refs`; `evaluate` passes the PINNED profile's value and refuses, exit 6, a gold profile whose cap differs; its stdout JSON carries `certificate_cap`, null when unlimited) → per query `{"qid","cert_valid":bool,"reason":str}`: a SAT witness / partition counterexample must extend to a model of every gold interpretation plus the assumptions **and be maximal**; an UNSAT core must be unsatisfiable under gold; an UNRESOLVED decision must carry overlapping `missing` codes. Gold is a submission-format directory; `query_timeout_s` from its `profile.json` bounds each query (reason `timeout`).
- Output paths that name an input are refused (exit 2) before anything is loaded: the check covers the queries file, the answers file (`check`), the submission/gold directory and every file under it, by canonical path and by file identity (hard links included). Outputs are cleared before any work starts and removed again on any non-zero exit, so stale answers never remain. `check` prints gold validation errors as codes only.
- `profile.json`: `{"max_certificate_refs":int?,"max_expr_nodes":int,"max_bytes":int,"max_interpretations":int,"max_weight_bits":int,"query_timeout_s":float,"build_deadline_s":float,"spend_ceiling_usd":float,"max_expr_depth":int?}`. The engine reads the first five and `max_expr_depth`; unknown keys are ignored. `query_timeout_s` must be finite, >0 and <=1e9 (`profile_invalid`, exit 1). The Python validator additionally requires finite values, positive integers in the u64 range (`max_weight_bits` <= u32), and `query_timeout_s` in (0, 1e7].
- Base consistency: if any declared interpretation (its bindings plus its constraints, no hypothesis) is unsatisfiable, `eval` and `check` exit 1 with a JSON error list on stderr (`code: inconsistent_base`) and write no output. Hypothesis inconsistency is separate (`hyp_inconsistent`).
- `check` verdict `reason` vocabulary: `ok`, `witness_invalid`, `witness_not_maximal`, `core_invalid`, `core_not_unsat`, `claim_not_entailed`, `counterexample_invalid`, `counterexample_not_maximal`, `claim_not_violated`, `decision_not_unresolved`, `decision_invalid`, `missing_invalid`, `family_not_certified`, `query_invalid`, `missing_answer`, `answer_error`, `timeout`, `engine_error`. Reasons never name interpretations, IDs or gold values. Closure and selection are `family_not_certified` by design.
- Timeouts: `eval` reads `query_timeout_s` from `<submission_dir>/profile.json` (absent = unlimited) and bounds every query's wall clock (checked between and inside SAT calls); an over-limit query answers `{"qid","error":"timeout"}`, which scores 0, and evaluation continues.
- Scaling: the engine splits the theory into independent components (IDs/aliases linked by constraints and bindings) and answers each query on just the components it touches; everything else comes from a cached per-component base classification. `MB_MONOLITH=1` forces one solver over the whole theory (differential testing); `MB_TIMING=1` prints per-query seconds on stderr, then stage lines for `eval` (`stage<TAB>name<TAB>seconds`: load, validate, read_queries, world_new, base, queries, answer, certify; load and validate also print for other commands). Output is deterministic (byte-identical across runs and processes).
- Exit codes: 0 ok; 1 invalid submission, invalid profile or inconsistent base; 2 usage/IO, missing directory, duplicate qid in queries, refused output path, internal panic.

## Python CLI (`python -m mentat_bench`)
`build`, `seal`, `evaluate`, `score`, and `fixtures gen|gold`. `build` requires `--corpus <corpus.jsonl>`. `evaluate` requires `--profile <pinned profile.json>` and `--expected-digest <digest printed by seal>`; it checks the seal, the pinned profile (and that `<submission>/profile.json` equals it), `usage.json`, then runs `mb-engine validate/eval/check`. `evaluate` copies the submission, verifies the copy against the pinned digest, runs everything on the copy, and re-verifies the original before publishing. Earlier `answers.jsonl`/`verdicts.jsonl` in `--out` are deleted first, on every refusal and on every failure; results are published only on full success (one line per query). `score --gold-bindings <gold/bindings.jsonl>` adds a `weighted` block (global class weights: 1/|class| over bound outcomes, 1.0 for unresolved; `exact`, `per_query` and the top-level `Q_N` stay unweighted) and `score --design <gold/query_design.jsonl>` adds `anchor` and `active` blocks (`{"queries":0,"Q_N":null,"status":"not_applicable"}` when empty, `no_design` without a design file; both blocks are always present). `score` treats a missing answers file as empty (every query scores 0, warning on stderr) and a missing verdicts file as no certificates; unreadable queries/gold are exit 2.
Exit codes: 0 ok; 2 usage/IO; 3 build aborted or incomplete (adapter fatal, no valid checkpoint, an OSError after the first checkpoint, or base theory not verified before the deadline: the work dir is kept so `fixed.finalize_checkpoint(<work>, <out>, profile)` can be retried with a larger deadline); 4 seal failure (tamper, ledger, link, wrong digest, incomplete-build refusal); 5 submission refused by the engine (invalid submission, inconsistent base theory — also at build time —, wall-clock overrun); 6 profile/usage/profile-mismatch refusal; 7 evaluator infrastructure failure (engine crash, missing binary, output count mismatch, failed publish). `build` accepts `--max-consecutive-errors` (default 20), `--max-relation-drops` (default 20000), `--local-protocol {1,2}`, `--no-groups`, `--group-sources`, `--group-max-members` (default 64, max 256), `--group-budget-frac` (default 0.25 of the spend ceiling and of the deadline left when the group phase starts) and `--max-group-calls` (default 20000), and the base-consistency flags `--no-admit`, `--admit-max-literals` (default 131072), `--relation-floor` and `--repair-budget-s` (see Base consistency below); a group-phase limit sets `group_budget_stopped` and ends only that phase, while a group-phase adapter failure is `adapter_fatal` (exit 3, not sealed). Build summary keys for repaired and resumed runs: `relations_asked`, `relations_dropped`, `contradiction_rate`, `groups_committed`, `groups_dropped`, `groups_dropped_pct`, `base_repaired` (true when any relation or group was dropped to restore a consistent base: per spec s9 an inconsistent base theory fails its universe, so the repaired score is reported next to a `strict Q_N` that is 0.0 for repaired cells), `prune_method`, `prune_seconds`, `admit_mode` (see Base consistency below), `admit_rejected_relations`, `admit_rejected_groups`, `admit_seconds`, `deferred_infeasible_dropped`, `deferred_infeasible_downgraded`, `deferred_unresolved`, `deferred_check_skipped` (see Base consistency), `resumed`, `prior_calls`; a work dir may contain `stall_trace.txt` (written only after 900 s without a progress heartbeat). Every candidate pair is asked (pairs inside accepted groups are not skipped). `--gold` with the gold_view adapter also lets the build report `group_recall` (candidate coverage: the share of gold groups contained in some candidate, not decided coverage), `gold_groups`, `gold_pairs` and `blocking_recall`; the oracle (full replay) skips blocking, so it reports only group recall; the adapter is aborted after that many consecutive failures or when more than half of >=100 decisions failed.

**Base consistency (admission).** A build's base theory must be satisfiable (the engine refuses an inconsistent base), and
the model's relations contradict the bindings and each other. At finalize, the base is made consistent by admission
(`--no-admit` turns it off and selects the post-hoc repair): the units are taken in one order, and a unit is admitted only if
the bindings plus the admitted units stay satisfiable (an exact 2-CNF check on a transitive closure of the implication
graph, kept as a bit matrix). A deferred cardinality part (at least k members true; the at-least-one of an exactly_one over
3 or more members) is also refused when fewer than k of its members are still possibly true; that is a necessary condition,
and the engine localizes what remains. The order is tiered: first the sibling-grade groups (`exactly_one`, `at_most_one`,
and `at_most_k` with k 1) in log order; then the relation decisions: those with a child-sent `conf` (highest first), then
those without, in the study's tie-break order (same market before same event title before the rest, then question-token
Jaccard overlap, highest first); then the other groups (`ordered_chain`, `at_least_k`, ...) by conf. A derived
(complement-dedup) relation follows its representative. `--relation-floor` drops the relations whose conf is below it on
the pairwise path (admission and the repair alike); a floored relation is not a contradiction (`floor_dropped_relations`; it is not in `relations_dropped`,
`contradiction_rate` or `base_repaired`).

Drops are counted per unit for relations and per group row for groups (a group with any dropped link is one group drop;
`groups_dropped` and `groups_dropped_pct` are rows over the committed rows). Admission refusals are drops: they go through
the drop ledger, so the caps apply (defaults: `--max-relation-drops` 20000 and `--max-relation-drop-frac` 0.25 of the
relations asked; `--max-group-drops` 20000 and `--max-group-drop-frac` 0.9 of the committed groups; the group defaults were
raised to admit the measured toy10k-0.5B refusals, 6,881 of 9,322 rows). mb-engine's localization of deferred parts counts
its rounds (`engine_rounds`), probes (`engine_probes`) and drops (`engine_localized_drops`), and its drops use the same group
cap.

Before mb-engine is asked, a deferred part that is impossible against N0 is dropped without it (`deferred_infeasible_dropped`,
one group drop per row). N0 is the bindings and the non-deferred live 2-CNF units (`_drop_infeasible_deferred`, the closure of
harness/admit.py). The deferred parts' own clauses are left out of N0 on purpose: a deferred exactly_one's at most one enters a
localization probe only while its unit is in the probe's prefix, so N0 must not contain it. The closure admission built is
reused when no live deferred unit has clauses; otherwise N0's closure is rebuilt here without the derived relations (which
their representatives imply). An at_most_k is impossible when more than k of its members are true in every model of N0 (the
forced-true members plus a greedy set of disjoint pairs x or y that N0 implies: `admit.at_most_possible`). An at_least_k, or an
exactly_one, is impossible when fewer than k of its members are not forced false by N0 (`admit.at_least_possible`). An at_most_k
or at_least_k is dropped. An exactly_one is downgraded (`groups_downgraded`), not dropped: its at most one is implied by N0 when
all its members are forced false, so the at most one changes no probe, and the localization downgrades it too.
Why this ends in the localization's base (when the localization finishes under the round cap): every probe's base contains N0,
so a part impossible against N0 is refused by every probe that contains it. The localization's first culprit is therefore that
part or an earlier one, and the part is removed when it would be reached; the probes that do not contain it are unchanged. The
test suite checks the equality against the localization on random small theories and on a two-exactly_one fixture
(tests/test_admit.py). An earlier version counted the deferred exactly_ones' at most ones in the base and reached a different
base on that fixture (the one exactly_one interaction the localization does not see until it reaches the unit).
The check covers unscoped theories within the admission bound, and runs only with mb-engine present, since the engine settle
is what it stands in for (without mb-engine the deferred parts stay unverified, as before). It does not run after the build
deadline, and a memory or numpy failure while the closure is built skips it too: the summary records the reason in
`deferred_check_skipped` ("deadline", "numpy" or "memory"), a warning goes to stderr, and the engine localizes the parts as before.
`deferred_infeasible_downgraded` counts the exactly_ones this check downgraded; the localization's own downgrades are not in it. On toy10k-1.5B it drops 570 at_most_k
rows and downgrades 7 exactly_one units before the engine is asked, and the engine then accepts the base with one probe and no
rounds. The localization drops one unit per round, so these 577 parts alone exceed the 200-round cap: without the check the
build reaches the cap and is sealed partial (`deferred_unresolved`) or fails.

Admission and the localization differ on one kind of unit, kept as it is: admission refuses an exactly_one whose at least one is
impossible (`admit_rejected_groups`; the unit, its at most one included, is refused), while the localization and this check
downgrade it and keep the at most one. Changing admission would change the admitted base of every build.

When the localization stops short, at the round cap (`MAX_GROUP_DROPS`) or at the build deadline, the deferred parts still live
are dropped (an exactly_one is downgraded) and the base is probed once (`_seal_unresolved`). An accepted base is sealed as a
partial build: the summary says `deferred_unresolved` (the number of parts left unresolved) and PARTIAL.json names that reason.
A refused base keeps the failure as before: an admitted base the engine refuses at the round cap falls back to the repair, and
a deadline stop raises BaseCheckIncomplete. The drops count against the group cap as localized drops do. The localization stops
one base probe early at the deadline (its clock is the time left less the duration of the last full-base probe), so the seal's
probe still has time. Like every engine probe, the seal's probe is bounded by the time left in the build deadline: past the
deadline no probe runs and the failure stands.
The seal's drops enter the group ledger only once the probe has accepted the base: a drop that overflows the group cap refuses the
seal, and the stop it would have replaced is raised as it is without a seal (on an admitted base the post-hoc repair runs next; on
the repair path itself the build fails, since that repair is not re-run). A probe that the deadline skips
is BaseCheckIncomplete, whatever stopped the localization, so the post-hoc repair does not run past the deadline. On scoped
theories the seal drops whole units, in every interpretation, as the localization does (the post-hoc repair clears only the
interpretation a conflict is in).

**Scoped settle (candidates builds).** Scoped relations are expressed as scoped 2-member ordered chains: a reading question
(a candidates row with source `reading` and exactly 5 members [u, o1..o4]) answers, per reading r, the chains [u, c] and [c, u]
with scope `{"axis": "reading", "values": [r], "of": ["alt", "base"]}`. A reading answer is normalized by
`adapters.base.reading_picks`, the rule the scorer uses: for each reading r, the counted chains (valid two-member ordered chains
over u and one option, with the implied order: a reverse chain flips it; scope None, or a reading scope whose `of` is
`["alt", "base"]` and whose values contain r) give one option c when they are exactly the two directions of one pair, `none`
when there are none, and `invalid` otherwise. The harness compiles, for each reading with an option c, ONE canonical pair
[u, c] and [c, u] scoped to that reading, so an unscoped or two-reading pair becomes one scoped pair per reading; `none` and
`invalid` compile nothing (`invalid` is one `groups_rejected`). Malformed and non-chain siblings are ignored. The raw answer
is logged unchanged in decisions.jsonl. Admission cannot take scoped units (it checks one
interpretation), so on a candidates build (policy `candidates_gold_informed`) whose scoped groups are all plain 2-CNF (none
deferred), the scoped units are held out of admission, the unscoped base is admitted as above, and then `_settle_scoped` runs
per interpretation. For an interpretation with scoped units, the base with them is checked; when that is unsatisfiable, or an
unscoped deferred at-least part (an exactly_one's at least one, an at_least_k) is left impossible by them, the scoped units are
walked in log order. The two links of a reading pair (the same two outcomes and the same bits, from one candidate call: each
reading row of groups.jsonl carries that call as `cand`) are one walk item, kept or lost whole. An item that cannot join the base and the items kept before it loses that interpretation's bit; a unit with no bit left
is dropped. A cleared bit and a dropped unit each count against the group cap, once per group row (the ledger counts a row
once). The settle stops at the build deadline (BaseCheckIncomplete). A MemoryError in the settle falls back to the post-hoc
repair (`repair_no_memory`) from the units as the snapshot took them. The summary keys `settle_cleared_bits` and `settle_dropped`
count the settle's cleared bits and dropped units; they appear only when the settle ran (not on a fallback). `admit_mode` stays `admit`. Other scoped theories, and scoped theories whose
settle does not apply, keep the post-hoc repair (`repair_scoped`). A reading build names its interpretations by the axis scheme
(`reading=base`, `reading=alt`), not by the gold fixture's `base` and `alt`; the engine uses interpretation names only as labels.

Admission is used for pairwise builds that have no scoped interpretation, or whose scoped units are settled (see
Scoped settle; `admit_mode` `repair_scoped` otherwise), with at most `--admit-max-literals` literals (2 x outcomes; the bit matrix is N^2/8 bytes, 2 GB at 131072, and admission peaks at about
three times the matrix: the matrix, the undo copy of the rows a unit touches, and the temporary of each row update), else `repair_size`. A
failed numpy import is `repair_no_numpy` and a failed allocation of the matrix `repair_no_memory` (numpy is declared in
pyproject). A failed 2-CNF check of the admitted set is `repair_unverified`. All three fall back to the post-hoc repair. The
admitted base is confirmed by mb-engine as before; an engine refusal that no deferred part localizes falls back to the
post-hoc repair (`repair_after_engine`), within the repair budget. The post-hoc repair (`_prune_in_process`) is the fallback
and the backstop.
The build deadline: model calls (bindings, blocking, groups, relations) stop at 0.95 x `build_deadline_s` (`FINALIZE_RESERVE_FRAC`
= 0.05; the reserve is recorded as the build's `finalize_reserve_s`); a call that crosses that point is discarded and charged. A stop
in the relation, group or blocking phase is `budget_stopped`, sealed with PARTIAL.json. A stop during bindings ends the build with
BuildIncomplete (no checkpoint exists yet, so nothing is sealable), as before but 5% earlier. This leaves finalize the rest, but does
not bound it: admission without a refusal may run past the deadline. The stop bounds the calls only for adapters that honour
`timeout_s` (the local adapter does). Admission stops at the deadline only after a unit was refused (BaseCheckIncomplete, the
checkpoint kept). A localization of deferred parts that the deadline or the round cap stops is sealed as a partial build when
the engine accepts the base with those parts dropped (Base consistency, `deferred_unresolved`).
A consistent admitted base is sealed even past the deadline, with no partial reason; its mb-engine confirmation is then
skipped (`base_probe` `skipped_deadline`). The repair path shares this engine skip.
`--repair-budget-s` bounds only the post-hoc repair, checked between repair passes. The repair runs when admission is refused or
does not apply (a scoped theory that is not settled, or 2 x outcomes above `--admit-max-literals`), and in the engine fallback. When the budget runs
out the build fails (RepairBudgetStopped, exit 3, nothing written, the checkpoint kept): finalize it again with a larger
`repair_budget_s`, and with a larger `build_deadline_s` when the deadline has passed too.
`--no-admit` takes `--repair-budget-s` and `--relation-floor` as well: both apply to the post-hoc repair, which `--no-admit` runs. `finalize_checkpoint` takes the admission knobs from the checkpoint's policy when they are not given; None is not a way
to clear a recorded `relation_floor` or `repair_budget_s`. A child's `conf` is optional (docs/local_protocol.md); a child without it is admitted in the
tie-break order above.

Strict scores: a cell whose base was repaired (`base_repaired`: a relation or group was dropped, not floored, or a group
lost an interpretation) reports `strict Q_N` 0; a base that was not repaired keeps its strict Q_N. A PARTIAL.json marks the
cell partial in its own right.

Environment: `MB_ENGINE` (path to `mb-engine`), `MB_ENGINE_TIMEOUT` (wall-clock budget for one engine run; default `600 + n_queries * query_timeout_s`).

## Known gaps (deferred by design)
Tuple weights for selection joins, N_active obligation records, scoped pairwise relations (the relation protocol cannot express interpretation-scoped relations; use group decisions with scopes), 1M-scale memory of the group phase.
